## Current implementation

- Kotlin/Spring backend follows DSA. Apply `.agents/skills/dsa/SKILL.md`; preserve thin entry points, domain ports, application transaction boundaries and transactional outbox. External provider and Shopify mutations occur outside transactions. Do not weaken architecture tests.
- Canonical `inputImages` lists flow through API, DB, queue and providers; legacy `image1`/`image2` remains supported. V4 stores/backfills `jobs.input_images`; V5 adds encrypted Shopify offline credentials and durable attachment state.
- JWT user routes under `/dashboard/**`; admin routes under `/admin/**` enforce ADMIN. Direct generation uses `X-API-KEY` under `/api/v1/**`. Registration does not grant admin. Free website subscription activation uses the existing checkout endpoint without Stripe.
- New authenticated GET `/dashboard/generation-options` reports configured provider/min/max photo count through `GetGenerationOptionsApplicationService`. Website submits repeated multipart `images` to POST `/api/v1/generate`, then polls `/dashboard/jobs` with JWT. Direct generation currently has no HTTP idempotency key: clients must not automatically retry uncertain POSTs.
- Provider selection applies to new tasks; existing tasks retain their provider. Meshy supports 1–4 photos; existing RunPod worker supports 1–2. No global four-photo ceiling. Backend upload defaults are 20 MB/photo and 85 MB/request, distinct from provider limits.
- Shopify generation binds a saved product and selected product image IDs or alternate uploads. Product binding, quota, job and outbox remain atomic. Background GLB attachment survives app closure, uses durable leases/media markers, and guards installation changes. Offline credentials are refreshed/exchanged automatically and encrypted with the persistent local AES key. Uninstall clears credentials/cancels attachments.
